# PROJECT PLAN — Personal Finance Manager

## 1. Название проекта

**Personal Finance Manager**

Рабочее русское название:

**Веб-приложение для управления личными финансами с автоматизированным распознаванием и анализом расходов**

---

## 2. Цель проекта

Разработать веб-приложение для управления личными финансами, которое позволит пользователю:

- учитывать доходы и расходы;
- распределять операции по категориям;
- устанавливать бюджеты;
- создавать финансовые цели;
- просматривать статистику и аналитику;
- загружать фотографии чеков;
- автоматически извлекать основные данные из чеков;
- автоматически определять или предлагать категорию расхода.

Проект должен представлять собой не только CRUD-приложение, но и включать отдельную ML-функциональность для обработки чеков.

---

## 3. Основной пользовательский сценарий

1. Пользователь регистрируется в системе.
2. Выполняет вход в аккаунт.
3. Добавляет доходы и расходы вручную.
4. Создаёт собственные категории расходов.
5. Устанавливает месячные бюджеты по категориям.
6. Создаёт финансовые цели.
7. Просматривает статистику доходов и расходов.
8. При необходимости загружает фотографию чека.
9. Backend отправляет изображение в отдельный ML-сервис.
10. ML-сервис извлекает данные из чека.
11. Пользователю показывается распознанная информация.
12. Пользователь подтверждает или исправляет данные.
13. Расход сохраняется в системе.

---

## 4. Основной функционал

### 4.1. Пользователи и авторизация

Необходимо реализовать:

- регистрацию;
- вход;
- выход;
- хранение паролей в безопасном виде;
- защиту пользовательских данных;
- доступ пользователя только к собственным финансовым данным.

---

### 4.2. Доходы и расходы

Пользователь должен иметь возможность:

- добавить доход;
- добавить расход;
- изменить операцию;
- удалить операцию;
- посмотреть список операций;
- фильтровать операции по дате;
- фильтровать операции по категории;
- просматривать операции за выбранный период.

Пример операции:

```text
Тип: EXPENSE
Сумма: 23.50 EUR
Категория: Food
Дата: 2026-09-21
Описание: LIDL
```

---

### 4.3. Категории

Пользователь сможет использовать категории, например:

- Food
- Transport
- Entertainment
- Shopping
- Health
- Utilities
- Salary
- Other

В дальнейшем пользователь сможет создавать собственные категории.

---

### 4.4. Бюджеты

Пользователь сможет устанавливать месячный бюджет для категории.

Пример:

```text
Food
Лимит: 300 EUR
Потрачено: 220 EUR
Осталось: 80 EUR
```

Backend должен рассчитывать:

- сколько уже потрачено;
- сколько осталось;
- превышен ли бюджет.

---

### 4.5. Финансовые цели

Пользователь сможет создавать финансовые цели.

Пример:

```text
Цель: Новый ноутбук
Необходимая сумма: 1500 EUR
Накоплено: 600 EUR
Прогресс: 40%
```

---

### 4.6. Статистика и аналитика

Необходимо отображать:

- расходы за месяц;
- доходы за месяц;
- баланс;
- расходы по категориям;
- сравнение доходов и расходов;
- изменение расходов по месяцам.

На frontend данные могут отображаться в виде:

- диаграмм;
- графиков;
- таблиц;
- карточек.

---

## 5. Распознавание чеков

Это одна из основных дополнительных функций проекта.

Пользователь загружает фотографию чека.

Общий процесс:

```text
Фото чека
    ↓
Spring Boot Backend
    ↓
Python ML Service
    ↓
ML-модель
    ↓
Распознанные данные
    ↓
Spring Boot Backend
    ↓
Проверка пользователем
    ↓
Сохранение расхода
```

Минимально необходимо извлекать:

- магазин / компанию;
- дату;
- итоговую сумму;
- валюту.

Пример результата:

```json
{
  "merchant": "LIDL",
  "date": "2026-09-21",
  "total": 24.73,
  "currency": "EUR"
}
```

Перед сохранением пользователь должен иметь возможность исправить распознанные данные.

---

## 6. Machine Learning

Планируется использовать готовую предварительно обученную модель.

Необходимо:

1. Найти подходящую pretrained-модель для обработки документов или чеков.
2. Найти подходящий открытый dataset чеков.
3. Запустить исходную модель.
4. Проверить качество её работы.
5. Выполнить fine-tuning модели на выбранном dataset.
6. Сравнить результаты до и после fine-tuning.
7. Сохранить дообученную модель.
8. Использовать её внутри Python ML Service.

На данном этапе не планируется создавать нейронную сеть с нуля.

---

## 7. Дополнительные функции на случай недостаточной сложности

Эти функции не относятся к обязательному MVP и реализуются только после основного функционала.

### 7.1. Определение регулярных платежей

Система анализирует историю операций и пытается определить повторяющиеся расходы.

Пример:

```text
Netflix — 12.99 EUR
каждый месяц
```

---

### 7.2. Обнаружение необычных расходов

Система сравнивает текущие траты пользователя с предыдущими периодами.

Пример:

```text
Обычно на Food: 280 EUR / месяц
Текущий месяц: 420 EUR

Уведомление:
Расходы на Food значительно выше обычного.
```

---

### 7.3. Прогнозирование расходов

На основе предыдущих месяцев система может рассчитывать приблизительный прогноз расходов на текущий или следующий месяц.

Эта функция рассматривается как дополнительная и не входит в первую версию проекта.

## 8. Предварительная архитектура

```text
                    User
                      │
                      ↓
                 React Frontend
                      │
                  REST API
                      │
                      ↓
              Java Spring Boot
                Main Backend
                 │        │
                 │        │ HTTP
                 │        ↓
                 │   Python ML Service
                 │        │
                 │        ↓
                 │     ML Model
                 │
                 ↓
              PostgreSQL
```

Роли компонентов:

**React**
- пользовательский интерфейс;
- формы;
- таблицы;
- графики;
- загрузка чеков.

**Spring Boot**
- основная бизнес-логика;
- авторизация;
- работа с пользователями;
- транзакции;
- категории;
- бюджеты;
- цели;
- аналитика;
- работа с базой данных;
- взаимодействие с Python ML Service.

**PostgreSQL**
- постоянное хранение данных.

**Python ML Service**
- загрузка ML-модели;
- обработка изображения;
- получение результата от модели;
- возврат структурированных данных Java backend.

## 12. Что НЕ нужно делать в самом начале

На старте проекта не требуется:

- сразу писать ML-модель;
- сразу делать Docker;
- сразу настраивать CI/CD;
- сразу делать весь frontend;
- сразу реализовывать дополнительные функции;
- создавать нейронную сеть с нуля.

Первый практический этап после планирования:

```text
Database Design
      ↓
Flyway
      ↓
Spring Boot
      ↓
основной Backend
```

После появления рабочего основного приложения можно переходить к ML, Docker и CI/CD.

## 14. Главный принцип разработки

Не пытаться реализовать весь проект одновременно.

Каждую новую функцию разрабатывать постепенно:

```text
Требование
   ↓
Database
   ↓
Migration
   ↓
Entity
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
DTO
   ↓
Tests
   ↓
Frontend
```

Перед реализацией каждого нового компонента необходимо понимать:

1. зачем он нужен;
2. какие данные получает;
3. какие данные возвращает;
4. где эти данные хранятся;
5. с какими другими компонентами он взаимодействует.
